# 433. app.zwipe.net answers an unknown path with 200

State: closed | Owner: halo | PR: release | Build seen: c313fb845

## Report
From the composer: app.zwipe.net answers every path with HTTP 200 (the single-page fallback), while zwipe.net returns real 404s since 425. A path that matches no route should get a 404 status while still serving the app shell, so the app draws its own not-found screen. Every real route (the dynamic `/:owner/deck/:slug/:token` and 419's `/guides` routes included) and every asset keeps its 200, and link previews keep working. The route list the check uses must not drift from the `Route` enum: generate it from the enum, or test that every variant matches. Checked with `curl -I`: a made-up path 404, real routes and a share link 200. Queued after 419.

## Fix
halo: a Pages middleware, `zwiper-web/functions/_middleware.js`, runs before every request on app.zwipe.net. A path that matches one of the app's routes keeps its answer, as does every file; any other path that Pages answers with the app's page (its single-page fallback) goes out with the same page and a 404, so the app still draws its own Page not found. The shared deck link's Function runs behind it unchanged. `ROUTES` in the middleware is the `Route` enum's paths (`:name` for a segment a route reads) and its redirects; a router test builds that list from `Route::flatten_site_map()` and the router's `#[redirect]` lines and fails when the two differ (it caught `/decks/:deck_id/cards`, 430's redirect). A dynamic segment matches any value, so `/decks/not-a-uuid` still gets a 200 and the app's own not found.

## Checked
`wrangler pages dev` over a local build with the functions:
- 404: `/no-such-page`, `/a/b/c/d/e`, `/nope.png`.
- 200: `/`, `/login`, `/guides`, `/guides/`, `/guides/filtering`, `/decks/123/edit`, `/decks/123/cards`, `/changelog`, a share link, its `/export`, `/robots.txt`, `/version.json`, a hashed CSS asset. `/index.html` is Pages' own 308 to `/`.
- The 404 body is the app's page (`div#main`, the wasm script).
- The share link's Function still answers a GET: a malformed token 404, and a well-formed token the live API doesn't know 404, its own rules. A HEAD (`curl -I`) skips that Function, which answers GET only, and gets the page with a 200, as before.

## Verification
The composer checked it live after the deploy, 2026-11-12: an unknown path answers 404, the routes 200.
